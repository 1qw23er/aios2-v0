# AIOS V0 P0-1 to P0-4 Design

## Scope

This increment implements only the first four P0 items from `CODEX_TASKS.md`:

1. A runnable FastAPI, SQLModel, Alembic, and pytest skeleton.
2. Project, Task, Event, Artifact, Agent, and Approval models plus an initial migration.
3. REST APIs for project creation, task creation, project-board queries, and approval submission.
4. A SQLite transactional-outbox event bus.

Orchestrator rules, external workstation import/export, full audit logging, and the end-to-end content workflow remain later P0 work.

## Architecture

The implementation will preserve the existing small package structure and add focused modules only where transaction boundaries or API contracts need isolation. FastAPI routes will use request/response DTOs rather than accepting database entities directly. Business operations that write both domain state and events will do so through one SQLModel session and one commit.

SQLite remains the default database. The database URL will be configurable through an environment variable so tests can use isolated temporary databases. SQLite foreign-key enforcement will be enabled for every connection.

## Startup and migrations

FastAPI will use a lifespan handler. Before the application accepts requests, the lifespan handler will run Alembic `upgrade head` against the configured database. A migration failure will abort startup rather than allow the service to run against an unknown schema.

The initial Alembic revision will create every table, index, unique constraint, and foreign key needed by P0-1 through P0-4. SQLModel `create_all` will not be the production schema-management path.

## Domain model

The six persisted domain entities are Project, Task, Event, Artifact, Agent, and Approval. Their fields and statuses follow `docs/02-domain-model.md`. Lists and structured metadata use JSON columns. IDs retain readable prefixes generated by the application. Timestamps are UTC.

The Event table is the V0 transactional outbox. In addition to the documented event fields, it stores processing state, attempt count, last error, and processed timestamp. `idempotency_key` is unique.

## REST API

The API will provide these P0-3 capabilities:

- Create a project from client-controlled fields while generating internal fields server-side.
- Create a task after validating its project, optional assigned agent, and dependency task IDs.
- Query a project board containing the project, tasks grouped by status, and pending approvals.
- Submit an approval request. An L4 action creates a pending approval record and does not execute the external action.

Missing referenced resources return HTTP 404. Structurally invalid input and invalid cross-project dependencies return HTTP 422. Database uniqueness conflicts return a stable HTTP 409 response.

## Transactional outbox

Business operations append their domain event in the same transaction as the domain mutation. Event insertion and domain changes either commit together or roll back together.

The P0-4 event-bus surface supports listing pending events in creation order and atomically marking one event processed or failed. A repeated idempotency key does not insert or dispatch a second event. Orchestrator consumption and dependent-task creation are explicitly deferred to P0-5.

## Testing strategy

Implementation follows red-green-refactor for every behavior:

- P0-1 tests cover migration, application startup, and health checks.
- P0-2 tests cover persistence, constraints, relationships, and migrated schema shape.
- P0-3 tests cover successful APIs and their 404, 409, and 422 paths.
- P0-4 tests prove same-transaction event writes, rollback behavior, idempotency, ordering, and processing transitions.

After each P0 item, the full pytest suite and Ruff checks will run, and README startup/migration documentation will be updated. Final verification will include editable installation, automatic migration on startup, the complete test suite, and Ruff.

## Operational constraints

The current machine provides Python 3.13 and 3.14 rather than exactly 3.12; both satisfy the declared `>=3.12` requirement. Verification will use an available interpreter and report its exact version.

The supplied directory is not currently a Git repository, so the design and implementation cannot be committed independently unless Git metadata is later provided or a new repository is explicitly authorized.
