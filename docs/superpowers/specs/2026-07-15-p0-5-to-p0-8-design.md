# AIOS V0 P0-5 to P0-8 Design

## Scope

This increment implements P0 items 5 through 8: deterministic orchestration, external workstation package validation and import, durable audit logging and idempotency, and one complete content-production end-to-end test. It does not add real model integrations, LangGraph, a web console, or any external L4 action.

## Orchestrator semantics

Tasks in a workflow are created before execution so the complete dependency graph is visible in the board. A downstream task lists upstream task IDs in `depends_on` and starts in `backlog`. Processing `task.completed` changes a downstream task to `ready` only when every referenced dependency is `done`.

The task-completion service changes the task to `done`, appends `task.completed`, and writes an audit record in one database transaction. The Orchestrator consumes pending outbox events in creation order. For every newly eligible task, it writes the `ready` state, a `task.ready` event, and an audit record atomically. Reprocessing the same completion event is a no-op for domain state and produces no duplicate ready event.

## External workstation packages

The adapter exports one directory per task containing `task_packet.json` and `context.md`. The packet is built from persisted Project and Task data and contains task ID, project identity and objective, role, instructions, input references, acceptance criteria, and a JSON Schema describing the expected result payload.

An external result contains a globally unique `result_id`, `task_id`, summary, claims, and artifacts. Pydantic validates the envelope, and the `jsonschema` package validates the result-specific payload against the packet's declared output schema. Imported claims remain unverified evidence and are not written to a context fact store.

A valid import stores an Artifact containing the normalized result, marks the task done, appends `task.completed`, and writes audit records in one transaction. A structurally invalid result changes the task to `rejected`, records a validation audit entry, and does not create a result Artifact or completion event. Reimporting the same `result_id` and payload returns the original Artifact; reusing the ID with different content returns a conflict.

## Audit log

A new immutable `AuditLog` table records actor, action, resource type and ID, project and optional task IDs, before and after JSON snapshots, idempotency key, and creation time. Application services, external import, and Orchestrator transitions append audit records in the same transaction as the state change they describe.

Audit payloads contain IDs, status, and non-secret business metadata only. Environment values, credentials, endpoint secrets, and raw prompt secrets are excluded.

## Approval boundary

The final approval workflow task becomes ready through the same dependency rule. The workflow coordinator creates a pending L4 Approval request for the final task. No publish, send, delete, payment, or customer commitment operation is represented or executed. Repeating orchestration cannot duplicate the approval request.

## End-to-end workflow

The acceptance test creates a persistent four-task chain:

1. Research through an external workstation.
2. Planning through a deterministic mock API agent.
3. Writing through an external workstation.
4. Human L4 approval.

It exports and imports research, processes the completion event, completes planning through the mock, processes its event, exports and imports writing, and processes the final transition. The test asserts task status at every boundary, exactly-once Artifacts and events under duplicate imports, one pending Approval, no external L4 execution, complete audit records, and persistence after opening a new database session.

## Error handling

Missing projects, tasks, dependency references, and package manifests are explicit errors. Invalid JSON or JSON Schema failures return structured validation errors. Database integrity failures roll back the associated domain state, event, Artifact, approval, and audit writes together. Event processing failures leave the event pending, increment its attempt count, and record the error for retry.

## Testing and delivery

Each P0 item follows red-green-refactor. After P0-5, P0-6, P0-7, and P0-8, the full pytest suite and Ruff checks run and README is updated. Final verification includes editable installation, the complete test suite, linting, persistence across sessions, and GitHub push to `main` after a reviewed commit.
